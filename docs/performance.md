# 原生运动核心的性能验证

桌面客户端的运动求解运行在 Rust 中。TypeScript 版本保留为浏览器演示／迁移参考；场景用的轻量正运动学与 Three.js 渲染仍在 WebView 内。不能仅根据语言名称推断加速比例，也不能把数学核心耗时当成点击按钮到完成绘制的总耗时。

## 可复现的检查

先构建真实 Rust 诊断程序，再执行前端及跨语言回归：

```sh
cargo build --locked -p emulation-core --bin core-cli
npm test
```

`tests/native-parity.test.ts` 通过 stdin/stdout 调用实际 `core-cli` 可执行文件，不使用 mock，也不会在找不到原生程序时跳过。默认查找 `target/debug/core-cli`（Windows 为 `.exe`），使用自定义 target 路径时支持 `CARGO_TARGET_DIR` 或 `EMULATION_NATIVE_CORE`。

检查包括两种型号的独立官方零位、完整 DH 链、确定性随机关节样本的全部有效逆解分支、整圈轴 6、固定／自动姿态、纯旋转、奇异起点、不可达目标、无效方向及仅端点可达的失败路径。比较不依赖逆解字符串 ID 或枚举顺序；四元数 q 与 -q 视作等价。恰好 60° 的浮点 `ceil` 可能令采样数量差 1，因此比较实际路径几何，而不是要求两个实现采样数逐字一致。

## 基准方法

```sh
node scripts/benchmark-native.mjs benchmark-result.json
```

脚本会以 Cargo release 配置构建 `examples/benchmark.rs`，并在临时目录将同仓库 TypeScript 参考核心编译为 Node.js 模块。它生成同一份 JSON 输入供两个实现读取。临时文件会在结束后清理；结果 JSON 包含机器、编译器、提交状态、统计值和原始批次耗时。

- 两款型号各测 FK、全部有效 IK、35 mm MoveL、TCP 定点 60° 旋转、自动方向搜索失败，另测长臂从示例起点到 `[200,0,100]` 的非平凡自动方向搜索，共十一组工作负载。
- 每组先预热 5 批，再测 31 批；FK 每批 2000 次、IK 100 次、35 mm MoveL 20 次、纯旋转 10 次、自动失败 20 次、非平凡自动方向搜索 5 次。
- 每种实现独立进程运行；第一轮 Rust → Node，第二轮 Node → Rust，减少固定执行顺序带来的偏差。没有同时运行两个基准进程。
- Rust 使用 `black_box`，FK／IK 在不同关节／方向样本之间轮换，两个实现都读取并累计结果，避免无用计算被消除。
- 统计量是每批耗时除以调用次数后的**批次均摊耗时**，中位数和 p95 来自两轮共 62 批。p95 不是单次请求的尾延迟；吞吐量是中位批次耗时的倒数。
- 输入解析、模型准备（FK／IK）、JSON 序列化、进程启动不进入计时。规划调用仍包含其实际模型查找、配置判断和结果分配。Node 已预热，Rust 为 release，而不是拿 release 对比未预热 JS 或 debug Rust。
- 未测量 Tauri IPC、WebView、GPU 渲染、安装包启动或完整用户操作延迟。共享机器调度、CPU 频率及不同平台都会影响结果。

## 实测记录

2026-11-09 同机执行完成，真实跨语言回归 **8 项通过**。基准期间暂停了其他 Cargo 构建及重型测试；没有并行运行两个被测实现。

- 环境：Linux x64，Intel Xeon Platinum 8573C（容器可见 3 个逻辑 CPU），内核 6.18.57。
- Rust 1.99.1，release `opt-level=3`、`lto=thin`、`codegen-units=1`，没有请求 `target-cpu=native`；Node.js 24.22.1。
- 测量时功能尚未提交，工作树为 dirty；[完整结果 JSON](performance-results.json) 保存了基线提交、测量时间、相关源码 SHA-256、每批原始耗时及结果校验和，避免将新代码结果误记为旧提交的成绩。
- 本次数字适用于上述共享 Linux 环境，尚未在用户的 Mac M5 或 Windows 上测量。Tauri IPC 和绘制耗时不在这张表内。

以下单位均为 **µs／次**，p95 为批次均摊耗时的 p95。最终记录将附当前环境与同机对照结果。


| 型号臂展 | 工作负载 | Rust 中位 | Rust p95 | JS 中位 | JS p95 | 中位对比 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |

| 0.58 m | 35 mm MoveL | 274.692 | 293.912 | 2050.933 | 2267.663 | 7.47× |

| 0.58 m | 明显不可达，自动姿态 | 0.448 | 0.458 | 1829.285 | 2008.850 | 早退策略差异 |
| 0.58 m | 自动搜索，方向变化 105° | 21456.607 | 22616.427 | 238076.933 | 261062.994 | 11.10× |
| 0.475 m | FK | 0.298 | 0.313 | 2.543 | 3.708 | 8.54× |
| 0.475 m | 全部 IK 分支 | 78.490 | 86.483 | 245.787 | 303.807 | 3.13× |
| 0.475 m | 35 mm MoveL | 276.988 | 299.664 | 2127.392 | 2320.372 | 7.68× |

常规 IK 约 3.1 倍、上述直线／旋转规划约 7.5–11.3 倍，来自当前 Rust 实现的原生编译、固定数组、减少中间结果分配和搜索优化共同作用。它不是一个脱离实现与工作负载的“Rust 对 JavaScript”语言倍数。

明显不可达目标会在 Rust 中先通过几何界限检查返回；旧 TypeScript 仍遍历姿态候选。因此该行主要体现新增的快速拒绝策略，不能拿它的数千倍差值描述一般逆解性能。自动搜索成功样例则实际检查约 575 mm 路径、选择方向变化 105°，测得约 21.46 ms 对 238.08 ms，未只使用“保持原方向即可成功”的简单情况。

两种实现的基准结果校验和按浮点容差核对；详细分支、配置、限位和路径几何由真实 `native-parity` 及 Rust 专项测试验证。每次修改数学实现后，应重新运行对应正确性检查；需要更新性能结论时，再用同一脚本测量并保留原始数据。
